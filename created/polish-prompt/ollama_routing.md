# Ollama routing (loaded by /polish-prompt when Ollama is set up)

## 1. Break the task into pieces
- **Judge each piece**: size XS to XL. Above XS defaults to Ollama.
- **Eligible**: code fixes, research, summaries, docs, boilerplate, first drafts. Security-sensitive code, 3+ files, migrations, billing or payments take the high-stakes row of the CLAUDE.md table. Summarising or reformatting takes the Boilerplate row.
- **Not eligible**: CLAUDE.md "Never delegate" list (git/deploy/merge/PR actions, physics/simulation correctness, data belonging to anyone other than the user, anything under `.claude/**`), your own data rules, if you keep any, per-project carve-outs, genuine architecture decisions.
- **Tool-access gap**: if the task needs any Claude Code-specific tool, skill or hook Ollama cannot call (MCP tools, Artifact, Workflow, skill invocations, hooks), Claude runs it itself first. Delegate post-fetch synthesis only when fetched content is large enough that drafting from it is the real token cost (a crawl, a long document, a bulk log). Small fetches or drafting needing final judgment stay on Claude. Bare `ollama run` cannot reach those tools; Track A workers can reach MCP tools, Skills and hooks when the global CLAUDE.md and worker settings allow them, so a fetch-then-summarise piece can go to Track A whole.
- **Scrub**: scrub logs and pasted text of emails, names and credentials before sending.

## 2. Who does each piece
- Choose exactly one `Who does it` value per piece.
- **Ollama Cloud**: writer, rigor and reviewer from the matching category row of the "Ollama Cloud delegation" table in `~/.claude/CLAUDE.md`. Never hardcode model names; the table is the single source. Reviewer is never the writer model.
- **Claude subagent**: haiku, sonnet or opus, tier from the SKILL.md settings table. Use for pieces Ollama cannot take: anything under `.claude/**`, your own data rules, per-project carve-outs, or a tool-access gap a subagent can cover. Also use for an XS piece, or one whose Ollama round trip costs more than the work (size floor exception), with the reason stated.
- **Main session**: only git/deploy/merge/PR actions, running tests, final verification, and tool-access-gap fetches.
- **Cline handover**: user runs it. Use for a piece that will plausibly pass about 60 turns, per the turn caps in `~/.claude/CLAUDE.md` or `ollama-addon/README.md`.
- **Expensive explicit-call model**: only when the user names it, or Claude recommends it and the user approves. Never default, never fallback.
- **Reviewer**: model never reviews its own output. Ollama pieces take the reviewer from the same CLAUDE.md row. A Claude subagent piece is reviewed by the main session; if the main session wrote it, by a subagent on a different Claude tier. Tests, git and deploy rows show reviewer: n/a, their pass/fail is the check. Verdict pieces (fan-in ranking, ticket review, final code review) are executed by the "Final review" row's reviewer model; the main session checks the verdict and still runs the tests, so Routing shows reviewer: main session.

## 3. Pick the execution path
- **Cline handover first for big live work**: if the task is M or larger and the Claude-session plan would delegate under 80%, offer a Cline handover instead. Claude writes `docs/handovers/<slug>_handover.md` in the project (goal, exact files, ordered steps, checks, stop condition, model). The user runs it in Cline on the Ollama writer model. Claude only final-checks the report. Also use it for any piece past about 60 turns (turn caps in `~/.claude/CLAUDE.md` or `ollama-addon/README.md`).
- **Usage check, only for M+ tasks or when the split is close**: if the `usage-live` skill is installed, run it for the Claude 5-hour and weekly percent; otherwise skip the Claude side. Ollama: `curl -s -H "Authorization: Bearer $OLLAMA_API_KEY" https://ollama.com/api/balance` returns `included.session` and `included.weekly`, each with `remaining_percent` and `resets_at` (legacy plans; credit-pool plans may lack them, then treat Ollama as available unless a call was rate-limited this session). Max 10 calls a minute. Send work to whichever side has more headroom: if Claude weekly is at or above 70 percent, or 5-hour at or above 80 percent, push every delegable piece to Ollama or a Cline handover and drop Settings to the lowest tier that covers the main-session pieces; if Ollama session or weekly remaining is under 15 percent, keep pieces on Claude subagents or wait for its `resets_at`.
- **Settings follow the main session's own pieces**: pick the tier from the SKILL.md settings table for the work the main session itself does. Opus high is right when those pieces need it (architecture judgment, reviewing a security or migration diff, consolidating conflicting reviews). When the main session only reads files, relays verdicts and runs git, the table gives haiku or sonnet.

## 4. Delegation loop and failure ladder
- **Delegation loop**: for eligible Ollama rows, run the loop instead of drafting directly. Write one precise, fully-scoped prompt (file, function, exact bug, desired outcome), call the best-fit Ollama Cloud model, review the result.
- **Apply directly**: apply with small cleanup fixed in-place; otherwise follow the failure ladder.
- **Failure ladder**: attempt 2 same model, sharper prompt, rigor up one; attempt 3 the row's "Rotate to" model; attempt 4 ask the user. A timeout rotates immediately. Never silently take over.
- **Stay on Claude**: testing, verification and any git action always stay on Claude regardless of who wrote the code.
- **Dispatch**: after approval, dispatch each Routing line on its named tier, not by the main agent approximating that tier itself. The main session does only the main-session rows.
- **Claude rows on the main model**: execute directly, no subagent needed.
- **Claude rows on a different model**: dispatch a real subagent on that exact model (opus, sonnet or haiku) via the Agent tool's `model` parameter. The main agent answering directly while trying harder is not a substitute. Encode the effort/thinking level into the subagent's task prompt as an explicit rigor instruction (the Agent tool has no separate effort/thinking parameter, only `model`). Do not imply effort/thinking is a hard toggle if asked; it is not, only the model is.
- **Ollama rows**: run the delegation loop above instead of drafting directly.

## 5. The delegation number
- **True ceiling**: push to the true ceiling, never anchor low. Before stating any delegation number, do the full piece-by-piece breakdown (each piece: mechanical/delegable vs judgment call, testing, git/deploy) and state the highest number it honestly supports on the first estimate. Do not open low and wait to be pushed higher. Only tool execution (tests, migrations, git/deploy) and final correctness verification are structurally non-delegable; everything else defaults to the Ollama-first draft. An honest 30% stays 30%; re-examine a task until the number reflects its delegable pieces.
- **Internal breakdown**: the breakdown is internal and auditable. The user sees one line only: `Delegation: ~X% (Ollama: <pieces>; Claude: <pieces>)`, under 25 words. Print the full per-piece table only when the user asks "show routing"; columns are Piece, Size, Delegable, Reason, Who does it, Reviewer.
- **Silent checks, never printed**: a delegable piece above XS left on Claude without a reason (size floor, CLAUDE.md "Ollama Cloud delegation") gets moved to Ollama; fan-out past the lane cap (`<TRACK_A_DIR>/max_parallel.txt`), turn caps outside the turn caps in `~/.claude/CLAUDE.md` or `ollama-addon/README.md`, or more parallel Claude subagents than usage rules allow gets batched to fit.
- **Recompute not raise**: a request to "increase delegation" triggers a full recompute from scratch, not a raise. Walk every piece again and re-evaluate each one. If the honest ceiling comes back unchanged, say so explicitly. Do not add 10 to 20 percent. If the user asked "show routing", print the revised per-piece table in the same format.
- **Banned hedge phrases**: "conservative estimate", "to start", "as a baseline", "we can go higher", or anything else that softens a number instead of committing. The number is either the ceiling the breakdown supports, or it is wrong.
- **Actual vs expected**: after the result, print `Delegation actual: ~X% (reason)` and compare it with the earlier estimate. At 0%, name the specific reason from section 1.
- **Report every dispatch, in one line**: after the result, `Delegated: <model> @ <rigor> x<calls>, escalated: no|yes, attempts: <N>`, one line for all calls. The per-call reports CLAUDE.md lists print only on "show routing" or when a call escalated.
